# TSO へ渡す見識（2026-08-30、ERS の1日から）

同じ人間の2つのプロジェクトで分析の質に開きがあるのは、片方で分かったことが
もう片方に渡っていないからである。この文書は **ERS で分かったことのうち、TSO に
そのまま効くもの**をまとめる。ERS 固有の事情は落としてある。

読む側の前提: TSO は `~/tactical-swing-os`。`docs/SPEC_REGIME_DECAY.md`（active）と
`docs/SPEC_CROSS_ASSET_REGIME.md`（draft / inactive）を持っている。

---

## 1. ローカルLLMは「安い」のではなく「動かない物差し」である

**これが一番大きい。**

前向きに評価を積むあいだ、採点に使うモデルが更新されれば同じ入力に違う値が出る。
十分な標本が溜まる前に、**標本の意味が途中で変わる**。APIモデルではこの再現性を
原理的に作れない。

重みが固定されたローカルモデルなら作れる。実測（ERS、2026-08-29）:

    mlx-community/Qwen3-8B-4bit / temperature=0 / 思考モード無効
    → 同じ入力に byte 一致の出力
    ピークメモリ 4.79GB（Apple M5 / 16GB で余裕）
    2,000トークンの日本語文書で約12秒

導入は `~/.venvs/` に venv を切って `pip install mlx-lm` だけ。conda base が
Python 3.8 だと MLX が入らないので、システム Python から venv を切る。

**TSO で効く場所**: ニュースのナラティブ分類（`NEWS_NARRATIVE`）。SPEC-CAR-001 が
入力候補に挙げているが、APIモデルで採点すると版が動いて標本が濁る。

## 2. 版に入れるものを間違えると、版が版として機能しない

ERS は「重みが固定されているから再現できる」と書いた ADR で、**Hugging Face の
リポジトリ名しか固定していなかった**。同じ名前が別の重みに解決されても digest は
動かない。**存在理由がそこで崩れていた。**

版に入れるべきもの:

| | |
| --- | --- |
| モデルの **commit** | リポジトリ名ではない |
| runtime の版 | `mlx-lm` / `mlx` / `transformers` / `tokenizers`。生成側が変われば出力が変わりうる |
| プロンプト | 全文 |
| 出力の語彙 | 選択肢の集合 |
| 温度・生成長・思考モード | |
| **前処理の規則** | ERS では「文書のどこを切り出すか」。ここを忘れやすい |

そして **digest の値そのものをテストで固定する**。「属性を差し替えたら digest が
動く」だけでは足りない——温度を 0.0 から 0.9 にしても、重みの commit を別物に
向けても、テストは通った（ERS で実測）。

**実行時に、固定した通りの環境かを検査して、違えば測らずに終える。** 宣言だけ
置いて確かめないと、別の runtime で測ったものが同じ版を名乗って記録に入る。

## 3. 版を変えたら、良くなったか確かめる。**失敗を除外しない**

ERS は「悪くなった版を採用しない」ために比較ツールを作り、その最初の実装が
**新しい版で失敗した文書を比較から外していた**。劣化が集合から消えるので、
悪くなった版が「変わっていない」ように見える。防ぐはずの失敗をツール自身がやった。

比較で見るもの:

1. **成否の移り変わりを、全文書について先に出す**（成功→失敗が何件か）
2. 閉じた語彙は一致率
3. 自由記述は 0件率と平均件数、失った件数と得た件数
4. 項目の集合が変わったら、増えた項目と消えた項目を挙げる（版が項目を足すのは想定内）

**実例**: プロンプトに「無ければ空配列」という6文字を足しただけで、理由の列挙が
崩壊した（0件が 21/74 → 51/74）。方向のような閉じた語彙は 100% 動かなかった。
**閉じた語彙は堅く、自由記述は脆い。**

## 4. 規則で読めるものを、モデルに推測させない

ERS は「業績予想が上方修正されたか」をモデルに尋ねていた。83件中52件が「上方」と
答え、**原文に修正の語があるのは2件だけ**だった。

原因は2つ:

- **入力にその情報が無かった。** 業績予想の記述は、切り出していた節の外にあった
- **語彙に「不明」を入れ忘れていた。** 他の3項目には在った。答えられないことを
  言う語を用意せずに、根拠が構造的に存在しない問いを立てていた

そして**短信には定型欄があった**（86%の文書で読める）。規則で読めば済む話だった。

**手順にする**:

1. その情報は入力に入っているか。**数えて確かめる**（ERS は97%と分かった）
2. 定型の欄や決まった書式で書かれていないか。**あれば規則で読む**
3. モデルに聞くのは、それでも残った曖昧なところだけ
4. **全項目の語彙に「不明」を置く**

## 5. 検証のやり方

### 変異が生き残るテストを探す

ERS で独立監査に変異を **137本**当てさせたところ、**64本が生き残った**。落ちなかった
ものの多くは、テストの名前と docstring が「守る」と宣言している性質そのものだった。

生き残った代表:

- `main()` を実行するテストが1本も無く、**既定で30倍取りに行く変異**が素通り
- 版の digest から構成要素を落としても通る
- プロンプトの極性を正反対にしても通る（縛っていたのは文字列2つだけ）
- 書き込みを見るはずのテストが `Path("x").write_text()` を見つけられない

### 文章ではなく挙動を見る

ERS で3回、テストが**自分の docstring に引っかかって**落ちた（`urlopen(` は
`open(` を含み、「鍵は決して出力しない」という説明文は `print` を含む）。
AST に変えたが、今度は**素の名前を許可する条件を書いて**書き込みを通した。

**ソースの字面を見る検査は、両方向に誤る。** 壊しても通り、直しても落ちる。
実行して結果を見る形に置き換える。

### 独立した監査を投げる

サブエージェントに「私の主張をコードとデータで確かめろ」と投げると、**別の
コンテキストで動くのでトークンも分割される**。ERS では6本並行で走らせた。
指示は「実測せよ、報告をそのまま信じるな、無理に見つけるな」。

## 6. 取得元の規律

### robots は実測する

「TDnet を一次ソースに」は一見自明だが、`www.release.tdnet.info` /
`www.xj-storage.jp` / `contents.xj-storage.jp` は **いずれも `User-Agent: *` /
`Disallow: /`** である。一方 `webapi.yanoshin.jp` は `Allow: /` に加え、AI エージェント
向けの `llms.txt` を公開している。

    curl -A "<name>" -H "Accept: text/plain, */*" <host>/robots.txt

`Accept: text/html, application/json` を使うと IIS 系は 406 を返して方針が読めない。
**robots.txt の全文を見ること。** 先頭が `User-agent: Googlebot` のこともある。

### 保存期間を先に測る

ERS は索引が7年遡れることを確認してから資料収集を設計し、**本文が約31日で消える**
ことに後で気づいた。254件のうち **132件は気づいた時点で既に失われていた**。

    curl で数ヶ月前の文書URLを叩き、200/404 の境界を測ってから設計する

### 取得と選別を分ける

選別（どの文書を採るか）を純粋関数にして、取得と混ぜない。混ぜると、テストの
たびにネットワークを叩くか、叩かないために選別を検査しないかのどちらかになる。
選別側が `urllib` / `httpx` を import しないことを**許可リスト**で縛る——
禁止リストは書き漏らしたものを通す（実際に `httpx` が通った）。

## 7. 数字を書く前の手順

Human の指摘（2026-08-30）:

> 私が謎用語（主語のない何を指すのかわからない確率等）の説明を聞いたら、
> そこから調べ直してあなたも理解し、中身のわからない数字のまま全く関係ない
> 計算に使ってたりして修正する羽目になった

**曖昧な言葉は、その数字を開けていない証拠である。**

数字を文に入れる前に、**何を、何のうち、どう測った数か**を言えるか確かめる。
言えないなら、それは数字ではなくラベルである。

ERS で実際に起きたもの:

| 書いたこと | 開けたら |
| --- | --- |
| 「偶然で出る確率」 | p値はそれではない |
| 「147社」 | 147**件**・145社。しかも同じ行に分母が3つ（147 / 145 / 142） |
| 「重みが固定されている」 | リポジトリ名しか固定していない |
| 「保有 +5」 | セッション番号で、3本保有 |
| `content_sha256` は同じものを見たか確かめる手掛かり | URLの包みが入るので再取得で変わる |

## 8. 「作った」と「使われている」を別に確かめる

ERS で**3回**同じ形を踏んだ。

1. 検証で使った補助関数を出荷しなかった（手元では通り、出荷したAPIでは通らない）
2. スナップショットを読んで数値を出す経路が出荷されていない
3. 規則で読む関数を書いて、呼ぶ経路を作らなかった

3回とも、気づいたのはレビュー側である。**モジュールにテストがあって、呼ぶ側が
無検査**という形が共通している。呼ぶ側を純粋関数に切り出して、そこもテストする。

## 9. 候補を属性として持つ

原因を1つずつ潰すと、潰すたびに全件を回し直すことになる。**先に候補を並べ、
それぞれを属性として持てる形にする。**

ERS の例（価格系列が壊れうる原因を26件列挙）:

    コーポレートアクション  分割・併合・配当落ち・優待落ち・増資・TOB
    銘柄の同一性            コード変更・表記・台帳の誤り・重複計上
    板の事情                ストップ高安・売買停止・特別気配・出来高ゼロ
    データ源                日次欠測・取得タイミング・過去の書き換え
    カレンダー              祝日・非営業日・オフセットの数え方
    台帳の意味論            日付が発表日でない・決算でない行

**未調査は `"unknown"` とする。`False` は「調べて、無かった」を意味する。**

そして**切る道具は、条件ごとに何件落としたかを返す**。母集団が変わったことに
気づかないまま数字を比べるのが、いちばん多い誤りである。

## 10. TSO 側で直接使えるもの

### SPEC-CAR-001 の非活性ゲートは正しい判断だった

ERS で同じ問いに突き当たった。期間差の原因を、株価指数でも四半期構成でも
金と暗号資産のレジームでも説明できなかった。**イベント日45日・期間2つでは、
どんな指標を足しても原因を割り当てられない。** SPEC-CAR-001 が
`clean closed evaluations >= 30` / `4資産以上` / `20日以上` で止めているのは、
同じ壁を先に見ていたということである。

### 資産リストに **銀** を足す

ERS で決め手になったのは **銅が動かず銀だけ +19%** だった。銀は産業金属でも
貴金属でもあるので、銅と揃って上がれば産業需要、銅を置いて上がれば通貨側になる。
SPEC-CAR-001 の候補（SPX/NASDAQ/VIX/DXY/USDJPY/GOLD/WTI/BTC/ETH/US10Y）には
銀が無く、`commodity_shock` と `safe_haven_demand` を切り分けられない。

### 日経VIは Yahoo に無い

`^JNIV` は 404。米VIXで代理するなら、**代理であることを記録に残す**。

### SPEC-RD-001 の「ゲートは保守的に・検知は敏感に」は他所でも効く

ERS は銘柄の同一性を名前で照合しようとして、門にしたら254件中73件を落とした
（索引は表示名で `Ｇ－アストロスケール` `ＫＴＫ` のように略される）。**コードの形を
門にし、名前は記録するだけ**にして解決した。SPEC-RD-001 が decay 統計を情報列に
留めてゲートに使わないのと同じ形である。

### 逆に、ERS から TSO へ渡せるデータ

短信の索引は **2021年から1,473日・101,803件** を保存済み（`~/.ers-corpus/tdnet/`）。
日次の開示密度は市場の状態の一部であり、TSO の入力候補になりうる。
ただし ERS で試した「上方修正/下方修正の比」は**表題に方向が出ない**ので取れない
（方向は本文の中にある）。取れるのは密度と種別まで。
