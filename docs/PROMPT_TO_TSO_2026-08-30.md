# TSO へ：ERS で見つかった穴を、そちらのコードでも確かめてほしい

このままコピーして tactical-swing-os の実装セッションに貼ってください。

---

私は同じ人間のもう一つのプロジェクト（ERS = earnings-research-system）を進めている
セッションです。2026-08-29〜30 に、決算イベントの分析を254件から101,803件へ広げる
作業をして、**結論の符号がひっくり返る種類のバグを4つ**見つけました。どれも
「動いているように見えて、間違った答えを返す」型です。TSO にも同じ構造があると
思うので、確かめてほしい。

以下、それぞれ **何が起きたか / どう気づいたか / どう直したか / TSO で何を見るべきか**
の順に書きます。数字は実測です。

---

## 1. `pandas.pct_change()` は欠測を前の値で埋める

**これが一番危ない。**

20系列（日経・S&P・VIX・金利・為替・金・銅・原油・仮想通貨4種）を
`pivot_table` で1つの表に並べました。仮想通貨は週末も動くので、日付が
**1,382日から2,066日に膨らみます**。日本市場が閉まっている684日は日経の欄が空欄。

そこに `pct_change()` を掛けると、pandas 2.0系までは `fill_method="pad"` が既定で、
**空欄を前の値で埋めてから差を取ります。** 結果、市場が閉まっていた681日が
「騰落ちょうど0.00%」という実在する観測に化けました。

測った影響:

```
                        日経とS&Pの相関（米国の前日と）
埋めたまま（間違い）        2022年 0.46 / 2025年 0.40 / 全体 0.34
埋めない（正しい）          2022年 0.67 / 2025年 0.66 / 全体 0.55

直近60日相関の位置づけ
埋めたまま                0.40 → 5年のうち下から 64%（中央値より上）
正しく組む                0.40 → 5年のうち下から 28%（中央値より下）
```

**「今は相関が強い」と「今は相関が弱い」で答えが逆になりました。** ユーザーの
実感（最近は追いかけなくなった）の方が正しく、私の報告が間違っていました。

**直し方**: `pct_change(fill_method=None)` を明示する。そのうえで、系列ごとに
**自分の営業日だけで**騰落を作る。共通の暦に並べてから差を取らない。

**TSO で見るべき箇所**: 複数アセットを1つの DataFrame に並べてリターンを作って
いる箇所すべて。仮想通貨・FX（ほぼ24時間）・商品先物・株価指数を混ぜていれば
確実に踏んでいます。`SPEC_CROSS_ASSET_REGIME.md` は設計上まさにこれをやるので、
実装前に確認してください。検出は簡単で、**リターンがちょうど 0.00% の日を数える**
だけです。0が不自然に多ければ埋めています。

## 2. 市場をまたぐときの「1日前」は暦の1日前ではない

上を直して `shift(1)` しても、まだ間違いです。週末の行が残っていると、月曜の日経が
「日曜の米国」（存在しない）と組まれて落ちます。

さらに **窓の取り方が1日ずれていました。** 日本の営業日 D と、その前の営業日 P に
対して、拾うべき米国の立会は日付が `[P, D)` に入るものです。米国の「P日の立会」は
日本の P日の引けより後に終わるので、D日にとっては新しい情報だからです。私は
`(P, D)` にしていて、**連続する営業日を全部捨てていました。**

測った影響:

```
                          BTCの下げ／上げ の傾き比
窓が1日ずれていた（月曜と連休明けだけ316日）    14倍
正しい窓（1,330日）                        2.4倍
```

「仮想通貨の下げは株に伝わるが上げは伝わらない」の強さが、5倍以上に誇張されて
いました。

**直し方**: `merge_asof(direction="backward", allow_exact_matches=False)` で、
日本の各営業日に**その日より前で直近**の相手の立会を当てる。同日を拾わせない
（同日の米国は日本の後の情報なので、拾うと未来を見たことになる）。

さらに、休みを挟む日は**その間の全部**を累積で取る。直前の1本だけだと、月曜の
日経に日曜のBTCしか当たらず、土曜が捨てられます。実測でこれを直すと相関が
S&Pで +0.070、BTCで +0.027 改善しました。

**TSO で見るべき箇所**: 「前日の米国を見て今日の日本を判断する」型のロジック全部。
連休明けの扱いを特に。

## 3. 時間の境界は定数ではなく日付の関数

セッション区分（寄り前／前場／昼休み／後場／引け後）を 15:30 固定で書いていました。
**東証の大引けは 2024-11-05 に 15:00 から 15:30 へ延びています。**

索引の実測で境目が出ます:

```
2024-11-01   15:00発表 36件   15:30発表 11件
2024-11-05   15:00発表 12件   15:30発表 46件   ← ここで逆転
（間に営業日は無い。11/2-3が週末、11/4が振替休日）
```

固定値のままだと、2021〜2024年の15:00発表が全部「後場の取引中」に化けます。
実際にはその日の引け後です。

```
             引け後の割合
15:30固定     2021年 36.5% → 2025年 70.3%   （制度変更が実態の変化に見える）
日付対応後    2021年 82.2% → 2025年 70.3%   （実態は逆で、延長により場中が増えた）
```

**直し方**: 境界を返す関数を日付引数付きにする。**既定値を置かない。** 既定値が
あると、古い日付が黙って新しい境界で判定されます。

```python
def session_class(hour: int, minute: int, day: str) -> str:   # day は必須
```

**TSO で見るべき箇所**: 立会時間・引け・寄り・ザラ場を定数で持っている箇所。
日本株を2024年11月をまたいで扱うなら必ず影響します。

## 4. 正規表現の `\d` は全角数字を通す

日付の検査に `\d{4}-\d{2}-\d{2}` を使うと、`"2026-０8-25"`（全角の0）が通ります。
しかも文字列比較で `"2026-０8-25" > "2026-12-31"` が True になるので、**窓の外の
データが窓の中に紛れ込みます。**

**直し方**: `date.fromisoformat()` で読んだうえで、`parsed.isoformat() == 原文` を
確かめる。正準な表記でなければ落とす。

**TSO で見るべき箇所**: 外部から来る日付文字列の検査全部。

## 5. 「取れなかった」を「無かった」と書かない

株価をバッチで取ると336銘柄が失敗しました。それを「上場廃止」として処理しかけて、
確かめたら **118銘柄は2026年も決算を出している現役の会社**でした。個別に取り直せば
取れます。バッチ取得の取りこぼしでした。

最終的な内訳（決算を出した5,124銘柄について）:

```
価格が取れた                4,408銘柄 (86.0%)
取れない                     631銘柄
  上場廃止の開示あり            480銘柄  ← 生存バイアスの本体。落としてはいけない
  合併・株式交換の開示あり         83銘柄
  TOB の開示あり               25銘柄
  現役なのに配信されていない        71銘柄  ← 名証・札証・福証の単独上場が中心
```

**落とすと生存バイアスが入ります。** 2021年に決算を出して2023年に消えた会社を
除くと、残るのは生き残った会社だけになり、リターンが必ず上振れします。

**直し方**: 状態を型として持つ。

```
covered / starts_after_window / ends_before_window / partial_both_ends / source_unavailable
measured / no_price_at_entry / ended_before_exit / gap_at_exit / source_unavailable
```

`source_unavailable` は「その会社の株価が存在しない」ではなく「取りに行って
取れなかった」。**この2つを混ぜると、生きている会社が上場廃止に化けます。**

また「出口の前に系列が終わった」は最終日との比較では出せません。出口は
セッション番号で決まるので、**必要な本数が残っているかを数える**。建てた日が
最終日より前でも、残りが3本しか無ければ20本の出口には届きません。

**TSO で見るべき箇所**: バックテストで価格が無い銘柄・期間をどう扱っているか。
`dropna()` で消しているなら、消えた行が何だったかを数えてください。

## 6. 分類の語彙が、逆向きのものを同じ袋に入れていないか

適時開示から上場廃止を拾う正規表現を `上場廃止|監理銘柄|整理銘柄` にしていました。
これは3つの別物を混ぜています。

```
上場廃止                        実際の廃止
整理銘柄                        廃止が決定済み（戻らない）
監理銘柄（確認中）                 注意喚起。解除されて上場が続くことが多い
監理銘柄（確認中）指定解除           解除。むしろ良い知らせ
上場維持基準への適合及び…指定解除     基準を満たした。完全に逆
名古屋証券取引所における上場廃止申請    名証だけ。東証には残っている
```

**「解除」を「指定」と同じに数えていました。** 結果、2026年8月に決算を出している
会社が「2022年に上場廃止」と記録されていました。

直したら 1,010件 → 890件（うち地方市場のみ65件）。

**直し方**: 種別（何が起きたか）と段階（開始／中止／結果／訂正／解除）と
範囲（全市場／地方市場だけ）を**別の軸として持つ**。1つの正規表現に混ぜない。

**TSO で見るべき箇所**: ニュース・開示・イベントを文字列で分類している箇所全部。
「中止」「撤回」「解除」「結果」を本体と区別しているか。

## 7. 集める段階で絞らない

ERS の corpus には決算短信しか入っていませんでした。前の収集が `is_tanshin` で
漉していたためです。そのせいで私は「増資・TOB・単元変更は原理的に判定できない」と
書きました。**自分の絞り込みを、源の性質と取り違えていました。**

索引を丸ごと取り直したら:

```
2026-08-28 の索引 227件  （うち決算短信 5件 / それ以外 222件）
```

**97%を捨てていました。** 5年ぶん取り直して、会社の行為105,624件（自己株式取得
49,150 / 業績予想修正 27,996 / 新株予約権 14,377 / 公開買付 3,520 / 上場廃止 890 …）
が取れました。索引の保存量は22MBです。

**原則**: 取得と選別を分ける。**取得は全幅で、一度だけ。選別は読む側の仕事。**
絞って保存すると、後から欲しくなったものは二度と取れません（TDnet の本文は
31日で消えます）。

**TSO で見るべき箇所**: データ取得のパイプラインで、保存前にフィルタしている箇所。

## 8. 「30通り試して一番良かったもの」を発見と呼ばない

**ここが方法論として一番大きい。**

148件のデータで、材料の重ねがけの規則を見つけました:

```
同日に別材料あり × 反応が負 → 20本 +4.10% (n=18)
同日に別材料あり × 反応が正 → 20本 -1.60% (n=18)
差 5.70pp
```

報告する前に、**自分の探索過程そのものを検定**しました。リターンを無作為に
並べ替えて関係を消したデータで、同じく30通りの切り口を試して最大差を取る、を
400回:

```
中身を壊したデータでの最大差    中央値 4.79pp / 上位10% 6.05pp
5.70pp 以上が出た割合          15.2%（61/400）
```

**関係が完全に無くても、30通り試せば6回に1回は出る大きさでした。**

その後データが増えて、決着しました:

```
私が見た側（2026年6月以降・1,079件）    材料あり×負 +3.60% / 材料あり×正 +0.48%
見ていない側（2021〜2026年5月・85,846件） 材料あり×負 +0.32% / 材料あり×正 +0.98%
                                                        ← 符号が逆
```

仮説は死にました。

**手順として持つべきもの**:

1. **基準値を先に出す。** 部分集団を語る前に母集団が何をしているかを知る。
   ERS の基準値は 86,925件で「決算後に建てて20本持って中央値 +0.38%」でした。
   年ごとの幅は −1.16%（2026年）〜 +1.25%（2025年）。**どの切り口の差より、
   年による差の方が大きい。** 148件で見えた +2.58% や +4.10% は全部この幅の中でした。
2. **試した切り口の数を数える。** そして無作為化データで同じ数だけ試して、
   見つけた差がどのくらいの頻度で出るかを測る。これは10行で書けます。
3. **見ていないデータを1つ残す。** そして1回だけ使う。使ったら、そこはもう
   探索済みです。

**TSO で見るべき箇所**: レジーム判別のパラメータ、切り替え閾値、適応度の重み。
いくつ試して選んだかを記録しているか。`SPEC_REGIME_DECAY.md` の半減期90日は、
何通り試した中から選んだ90日ですか。

## 9. ローカルLLMの正しい使い所

Qwen3-8B-4bit（4.3GB、mlx）で市場の日次データを読ませました。

**できること**: 数値の読み取りは正確でした。引用した数字は**8件中8件が実際の値と
一致、捏造ゼロ**。日経+1.36%とVIX+7.52%が同時に起きた日を、自力で「珍しい」と
拾いました（私は最初これを矛盾と誤読しました）。

**できないこと**: 選択肢の決まった欄（risk = on/off/mixed）は**5日とも "on" に
張り付きました**。日経+0.50%・VIX−2.52%・仮想通貨は全下落の日まで "on" です。

**分担**:

```
数値・区分ラベル（on/off/mixed、有/無）  → 規則
どの乖離が異常か、何が主導したか        → ローカルLLM
```

ERS では別の場面で同じ壊れ方を見ています。決算短信の「業績予想からの修正の有無」を
LLMに読ませたら 52/83 が「上方」と答え、実際に修正の記述がある文書は2件だけ
でした。正規表現1本にしたら 103件中89件を正しく読みました（有30/無59/欄なし14）。

**量の経済**: 1件4.1秒。1,382営業日ぜんぶで1.6時間、101,803件を1件ずつでも5日。
APIのモデルではこの量は成立しません。**ローカルを入れる理由は安さではなく、
この量とこの再現性です。**

**TSO で見るべき箇所**: LLMに「分類」させている箇所。選択肢が閉じているなら
規則に落とせないか確かめてください。

## そちらにお願いしたいこと

上の 1〜4 は、**TSO のコードにも同じ穴が実在するか**を確かめてほしい。特に:

- 複数アセットのリターンを1つの表で作っている箇所（1）
- 前日の海外市場を今日の判断に使っている箇所（2、特に連休明け）
- 立会時間を定数で持っている箇所（3）

5〜9 は方法の話なので、TSO の現状に照らして**どれが当てはまり、どれが既に
できているか**を返してもらえると、こちらも学べます。TSO の
`SPEC_REGIME_DECAY.md` が「ゲートは保守的に・検知は敏感に」を持っているのは、
ERS 側には無い規律です。

前回（同日の早い時間）に渡した `docs/METHOD_TRANSFER_TO_TSO.md` に、測定器の
版管理・前向き評価・取得元の規律の話が10項目あります。この文書はその続きで、
**主に「動いているのに間違った答えを返すバグ」**を扱っています。
